# Redis и Kafka

## Redis
Redis — быстрое я хранюлище структур данных в памяти. Его часто используют для кэша.

### Cache-aside
1. Приложение ищет значение в Redis.
2. Если оно есть — возвращает.
3. Если нет — читает из БД.
4. Записывает значение в Redis с TTL.
5. Возвращает результат.

TTL — срок жизни ключа. После истечения Redis может удалить его.

Проблемы: устаревшие данные, cache stampede (много запросов одновременно заполняют один отсутствующий ключ), слишком большой кэш, недоступность Redis.

## Kafka
Kafka — распределённая платформа потоковой передачи событий.
- Topic — именованный поток сообщений.
- Partition — часть топика, упорядоченный журнал.
- Offset — позиция сообщения в partition.
- Producer — отправляет сообщения.
- Consumer — читает сообщения.
- Consumer Group — несколько потребителей делят партиции.

Порядок сообщений гарантируется внутри partition, но не глобально между всеми partition.

## Повторная доставка
Сообщение может быть обработано повторно. Обработчик должен быть идемпотентным: повтор события не создаёт повторный бизнес-эффект.

Изучаю retry/backoff, dead-letter topic, schema evolution, transactional outbox, consumer lag и дедупликацию.

## Redis: ключи и TTL

Выбирай понятную схему ключей, например `user:42:profile`. TTL ограничивает срок жизни кэша, но не гарантирует абсолютную синхронность с БД. Продумай инвалидацию при обновлении данных и поведение при недоступности Redis.

## Cache stampede

Когда популярный ключ истекает, много запросов одновременно идут в БД за одним значением. Возможные меры: single-flight/lock, случайный разброс TTL (jitter), предварительное обновление или stale-while-revalidate — в зависимости от требований.

## Kafka: delivery semantics

На практике потребитель должен быть готов к повторной доставке. Exactly-once гарантии Kafka имеют ограничения и не означают автоматическую exactly-once запись во внешнюю БД. Часто применяют идемпотентную обработку, уникальный event id и транзакционный outbox.

## Kafka: consumer group

Внутри одной consumer group партиция в данный момент назначается одному потребителю группы. Если потребителей больше, чем партиций, часть будет простаивать. Масштабирование параллелизма ограничено количеством партиций.

## Сообщение и схема

Событие должно содержать идентификатор, тип/версию схемы, время события и необходимые данные. Изменения схемы делай совместимыми с уже работающими producers/consumers; не предполагай, что все компоненты обновятся одновременно.
