# Тестирование Java-приложений

## Зачем тесты
Тест проверяет поведение программы и помогает заметить регрессию — ситуацию, когда новое изменение ломает ранее работавший сценарий.

## Виды
- Unit — небольшая единица логики изолированно.
- Integration — взаимодействие компонентов и зависимостей, например репозитория с PostgreSQL.
- End-to-end — сценарий через систему почти как реальный пользователь.

## JUnit 5
JUnit — фреймворк для написания и запуска тестов.

```java
@Test
void shouldRejectBlankTitle() {
    assertThrows(IllegalArgumentException.class,
        () -> new Task(" "));
}
```
Обычно тест состоит из Arrange (подготовка), Act (действие), Assert (проверка).

## Mockito
Mockito создаёт mock-объекты — подмены зависимостей, поведение которых задаётся в тесте. Я использую для изоляции внешней зависимости. Не мокируй всё подряд: тесты станут хрупкими и зависимыми от внутреннего устройства класса.

## Testcontainers
Позволяет запускать реальные зависимости, например PostgreSQL в контейнере, для интеграционных тестов.

## Что проверять
Успешный сценарий, границы, некорректный ввод, ошибки зависимостей, права доступа, транзакции и важные конкурентные ситуации. Coverage не равен качеству тестов.

## Пирамида тестов и границы

Обычно unit-тестов много и они быстрые; интеграционных меньше, они проверяют взаимодействие компонентов; end-to-end ещё дороже и покрывают критические пользовательские сценарии. Это ориентир, а не обязательная пропорция.

## Mockito — базовый пример

```java
@ExtendWith(MockitoExtension.class)
class TaskServiceTest {
    @Mock TaskRepository repository;
    @InjectMocks TaskService service;

    @Test
    void returnsTaskFromRepository() {
        when(repository.findById(1L)).thenReturn(Optional.of(new Task()));
        Task result = service.getById(1L);
        assertNotNull(result);
        verify(repository).findById(1L);
    }
}
```
Подстрой пример под реальные конструкторы и методы класса. Mock должен заменять внешнюю зависимость, а не повторять реализацию тестируемого класса.

## Что делает тест хорошим

- Проверяет наблюдаемое поведение, а не приватные детали.
- Имеет понятное имя и один основной сценарий.
- Не зависит от порядка запуска и реального времени без необходимости.
- Самостоятельно подготавливает данные и очищает ресурсы.
- Проверяет не только happy path, но и ошибки/границы.

## Testcontainers

Контейнерная БД помогает тестировать SQL и миграции на реальном движке, а не на H2, поведение которой может отличаться от PostgreSQL. Учитывай время запуска контейнера и наличие Docker в CI.


## Параметризованные тесты

Если один сценарий проверяется на разных входах, я использую `@ParameterizedTest` вместе с `@ValueSource`, `@CsvSource` или `@MethodSource`. Так меньше копипаста и виднее набор проверяемых случаев.

## Тесты контроллеров и репозиториев

Для web-слоя проверяй HTTP-статус, тело, валидацию и права доступа. Для репозитория проверяй реальные запросы и mapping на той же СУБД, что используется приложением (например, PostgreSQL через Testcontainers). Выбор slice-тестов или полного контекста зависит от того, какую границу нужно проверить.
