# Spring Security: основы

## Authentication и Authorization
- Authentication — кто пользователь?
- Authorization — что пользователю разрешено?
Успешный вход не означает, что пользователь может читать любые данные.

## Основные компоненты
- SecurityFilterChain — цепочка фильтров HTTP-запроса.
- Authentication — объект с данными о проверяемой/подтверждённой личности.
- AuthenticationProvider — механизм проверки учётных данных.
- UserDetailsService — загрузка пользователя.
- PasswordEncoder — хеширование и проверка паролей.
- Method Security — ограничения доступа на уровне методов.

Конфигурация зависит от версии Spring Security — я сверяюсь с документацией именно своей версии.

## Пароли
Я храню не исходный пароль, а стойкий password hash с солью. Я использую PasswordEncoder, не придумывай свой алгоритм и я не использую быстрое обычное хеширование как замену password hashing.

## CSRF и CORS
- CSRF — атака, при которой браузер отправляет нежелательный запрос с учётными данными пользователя.
- CORS — браузерный механизм, определяющий, каким origin разрешено читать ответы.
CORS не заменяет аутентификацию и авторизацию.

## Практика
Защити API: регистрация, вход, доступ владельца только к своим ресурсам, отдельная роль администратора, тесты разрешённого и запрещённого доступа.

## Типичный порядок защиты API

1. Запрос проходит security filters.
2. Механизм аутентификации проверяет credentials/token.
3. В SecurityContext помещается Authentication.
4. Правила доступа решают, разрешён ли запрос.
5. Контроллер/метод выполняет бизнес-логику.

## 401 и 403

- `401 Unauthorized` — запрос не прошёл аутентификацию или не содержит действительных учётных данных; часто нужен challenge/повторный вход.
- `403 Forbidden` — доступ запрещён, даже если пользователь аутентифицирован.

## Пароли и токены

Пароли хранят в виде адаптивного password hash (например, BCrypt/Argon2 через поддерживаемый PasswordEncoder), а не шифруют обратимым способом. Токен — bearer credential: тот, кто им владеет, может получить права токена. Не клади токены в URL и логи; задавай срок действия и механизм отзыва/ротации.

## CSRF и stateless API

CSRF особенно важен, когда браузер автоматически прикладывает cookie сессии. Отключать CSRF только потому, что API «REST», нельзя: решение зависит от способа передачи credentials и клиента. CORS — не механизм контроля доступа к данным на сервере.

## Проверка владения ресурсом

Одной роли `USER` недостаточно. При запросе `/users/{id}/orders/{orderId}` сервер обязан проверить, что заказ действительно принадлежит текущему пользователю или доступен ему по правилам. Не доверяй userId из тела запроса без проверки.
