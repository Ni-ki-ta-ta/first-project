# Многопоточность в Java

## Зачем нужна многопоточность

Многопоточность позволяет выполнять несколько задач конкурентно. Она полезна для I/O-bound задач (ожидание сети, диска) и CPU-bound задач (параллельные вычисления), но добавляет сложности: гонки, видимость памяти, deadlock и накладные расходы.

## Process и Thread

- Process — запущенный экземпляр программы с собственными ресурсами.
- Thread — поток выполнения внутри процесса.
- Потоки одного процесса разделяют heap, но у каждого потока свой stack.

Создание потока не означает, что код обязательно выполнится параллельно на отдельном ядре: планированием управляет JVM и ОС.

## Race condition

Race condition возникает, когда результат зависит от непредсказуемого порядка конкурентных операций.

```java
class Counter {
    private int value;

    void increment() {
        value++; // не атомарная операция
    }

    int get() {
        return value;
    }
}
```

`value++` состоит из чтения, увеличения и записи. Несколько потоков могут потерять обновления.

## synchronized

`synchronized` обеспечивает взаимное исключение для монитора и гарантии видимости памяти при входе/выходе из одного и того же монитора.

```java
class SafeCounter {
    private int value;

    synchronized void increment() {
        value++;
    }

    synchronized int get() {
        return value;
    }
}
```

Блокировка должна защищать общий инвариант, а не отдельную строку «для вида». Я стараюсь держать критическую секцию короткой и не выполнять внутри неё долгие сетевые вызовы.

## volatile

`volatile` обеспечивает видимость записи между потоками и определённые гарантии порядка, но не делает составные операции атомарными.

```java
private volatile boolean running = true;
```

Это подходит для флага остановки. Для `counter++` одного volatile недостаточно.

## Atomic классы и locks

`AtomicInteger`, `AtomicLong` и другие atomic-классы дают атомарные операции над отдельными значениями.

`ReentrantLock` предоставляет явное управление блокировкой, включая `tryLock` и возможность прерывания ожидания. Освобождаю lock в `finally`.

```java
lock.lock();
try {
    // критическая секция
} finally {
    lock.unlock();
}
```

## ExecutorService

Вместо ручного создания большого числа Thread обычно использую пул потоков.

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
try {
    Future<Integer> result = pool.submit(() -> 2 + 2);
    System.out.println(result.get());
} finally {
    pool.shutdown();
}
```

`shutdown()` запрещает новые задачи и позволяет завершить уже отправленные. `shutdownNow()` пытается прервать выполняющиеся задачи, но прерывание кооперативное: код должен корректно реагировать на interrupt.

## Callable, Future и CompletableFuture

- `Runnable` не возвращает результат.
- `Callable<T>` возвращает результат и может выбрасывать checked exception.
- `Future<T>` позволяет получить результат позже, отменить задачу или проверить завершение.
- `CompletableFuture<T>` позволяет строить цепочки асинхронных вычислений.

Я не вызываю `get()` без таймаута в критичном пути, если ожидание может зависнуть. Для асинхронных цепочек обрабатываю исключения и выбираю подходящий executor.

## Concurrent collections

- `ConcurrentHashMap` — потокобезопасная map для конкурентного доступа.
- `CopyOnWriteArrayList` — полезен, когда чтений значительно больше записей.
- `BlockingQueue` — очередь с блокирующими операциями, полезна для producer-consumer.
- `ConcurrentLinkedQueue` — неблокирующая конкурентная очередь.

Потокобезопасная коллекция не делает автоматически атомарной последовательность из нескольких операций. Для «проверить и затем добавить» нужна атомарная операция или синхронизация.

## Deadlock

Deadlock — взаимная блокировка: поток A держит lock 1 и ждёт lock 2, поток B держит lock 2 и ждёт lock 1.

Снижаю риск:
- беру несколько блокировок в едином порядке;
- сокращаю область блокировки;
- использую `tryLock` с таймаутом там, где это оправдано;
- не вызываю неизвестный внешний код под lock.

## Java Memory Model и happens-before

JMM описывает видимость и порядок операций между потоками. Happens-before задаёт гарантии: если действие A happens-before B, результаты A видимы B в рамках этих правил.

Гарантии появляются, например, через:
- освобождение и последующий захват одного monitor;
- запись volatile и последующее чтение того же поля;
- запуск потока до действий внутри него;
- завершение потока и успешный `join()`.

Без таких отношений нельзя полагаться на то, что другой поток сразу увидит обычную запись.
