# JVM, память и диагностика

## От исходного кода до выполнения

`javac` компилирует Java-код в bytecode (`.class`). JVM загружает классы, проверяет байткод и исполняет его. HotSpot может компилировать часто выполняемый код в машинный через JIT.

## Основные области памяти

- Heap — объекты и массивы; область разделяется потоками.
- Stack — отдельный стек вызовов у каждого потока; содержит frames методов и локальные данные.
- Metaspace в HotSpot — метаданные классов.
- Code Cache — скомпилированный JIT-код.

Ссылка на объект может находиться в локальной переменной, а сам объект — в heap. Не стоит запоминать упрощение «все примитивы в stack, все объекты в heap» как абсолютное правило: оптимизации JVM сложнее.

## Garbage Collector

GC освобождает объекты, которые недостижимы из GC roots. Он не удаляет объект только потому, что тот «логически больше не нужен».

Утечка памяти возможна, если приложение продолжает хранить ссылку: например, в static-коллекции, кэше без ограничения размера или незакрытом listener.

GC не гарантирует немедленное освобождение памяти и не заменяет управление ресурсами. Файлы, сокеты и соединения нужно закрывать явно.

## ClassLoader

ClassLoader загружает классы по мере необходимости. Важны bootstrap, platform и application class loaders, а также delegation model. Один и тот же класс с одинаковым именем, загруженный разными ClassLoader, может считаться разными типами.

## JIT и производительность

JIT использует profiling и оптимизации для часто выполняемого кода. Поэтому микробенчмарки нужно писать аккуратно: учитывать прогрев JVM, dead code elimination и использовать JMH, а не измерять один вызов через `System.nanoTime()`.

## Диагностика

```bash
jcmd -l
jcmd <pid> VM.version
jcmd <pid> GC.heap_info
jstack <pid>
```

- `jcmd -l` показывает JVM-процессы.
- `VM.version` показывает сведения о JVM.
- `GC.heap_info` показывает сведения о heap, если команда поддерживается.
- `jstack` помогает получить thread dump.

Для анализа использую Java Flight Recorder, heap dump, thread dump и профилировщик. Сначала фиксирую симптомы и собираю данные, затем формулирую гипотезу. Параметры GC не меняю наугад.

## Практика

1. Запускаю приложение с ограниченным heap и наблюдаю поведение.
2. Снимаю thread dump.
3. Снимаю heap dump и нахожу удерживаемые объекты.
4. Сравниваю поведение до и после исправления утечки.
5. Изучаю JFR и JMH.
