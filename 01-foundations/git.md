# Git и GitHub — подробная шпаргалка

## 1. Что такое Git

**Git — система контроля версий.** Она сохраняет историю изменений проекта. Можно посмотреть, кто и когда я изменяюл файл, сравнить версии, вернуться к прежнему состоянию и параллельно работать над разными задачами.

Git работает локально: история хранится на твоём компьютере. GitHub — сайт, на котором можно хранит удалённую копию репозитория, работать через Pull Request и сотрудничать с другими разработчиками.

**Репозиторий** — папка проекта вместе с историей Git.

## 2. Три области Git

Упрощённо у Git есть три области:

1. **Working directory** — обычные файлы проекта. Здесь я пишу код.
2. **Staging area (index)** — список изменений, которые я подготовил к следующему коммиту.
3. **Local repository** — сохранённая история коммитов.

Путь изменений:

```text
Файлы проекта
   |
   | git add
   v
Staging area
   |
   | git commit
   v
Локальная история Git
   |
   | git push
   v
Удалённый репозиторий (например, GitHub)
```

Зачем нужен staging: можно выбрать, какие именно изменения попадут в коммит. Не обязательно сохранять всё сразу.

## 3. Создание и получение репозитория

```bash
git init
```
Создаёт новый локальный репозиторий в текущей папке. Git начинает отслеживать историю этой папки.

```bash
git clone https://github.com/user/project.git
```
Скачивает удалённый репозиторий на компьютер, включая историю, и создаёт папку проекта.

**Разница:** `git init` начинает историю в существующей папке; `git clone` копирует уже существующий репозиторий.

## 4. Проверка состояния

```bash
git status
```
Показывает:
- какие файлы изменены;
- какие новые файлы ещё не отслеживаются;
- какие изменения уже подготовлены к коммиту;
- на какой ветке я нахожусь.

Запускай `git status` регулярно. Это одна из самых полезных команд.

```bash
git diff
```
Показывает изменения в отслеживаемых файлах, которые ещё не добавлены в staging.

```bash
git diff --staged
```
Показывает изменения, которые уже подготовлены к коммиту. Именно эти изменения я собираюсь сохранит.

```bash
git log --oneline --graph --decorate
```
Показывает историю коммитов в компактном виде. Удобно видеть ветки и точки слияния.

## 5. Подготовка изменений — git add

```bash
git add Main.java
```
Добавляет изменения конкретного файла в staging.

```bash
git add src/
```
Добавляет изменения внутри папки `src`.

```bash
git add .
```
Добавляет изменения из текущей папки и вложенных папок. Новые, изменённые и удаления файлов могут попасть в staging.

Важно: `git add` **не сохраняет коммит**. Он только готовит изменения к коммиту.

## 6. Сохранение — git commit

```bash
git commit -m "Add task validation"
```
Создаёт коммит из содержимого staging area. Коммит — сохранённая точка истории с автором, датой и сообщением.

Хорошее сообщение коротко отвечает на вопрос «что я изменяюлось»:
- `Add task validation`
- `Fix task status update`
- `Update README`

Плохое сообщение: `changes`, `fix`, `123`.

Коммит сохраняет только то, что было в staging. Если файл изменён, но не добавлен через `git add`, эти изменения не попадут в коммит.

## 7. Удалённый репозиторий — remote

Удалённый репозиторий — другая копия проекта, например на GitHub.

```bash
git remote -v
```
Показывает адреса настроенных удалённых репозиториев.

```bash
git remote add origin https://github.com/user/project.git
```
Добавляет удалённый репозиторий и называет его `origin`. `origin` — просто стандартное имя, его можно я изменяють.

## 8. Отправка изменений — git push

```bash
git push origin main
```

Разбираем команду:
- `git` — запускаем Git;
- `push` — отправить локальные коммиты в удалённый репозиторий;
- `origin` — имя удалённого репозитория;
- `main` — ветка, которую отправляем.

То есть команда публикует коммиты локальной ветки `main` в ветку `main` на GitHub.

```bash
git push -u origin feature/login
```
Отправляет ветку `feature/login` на GitHub и запоминает связь с удалённой веткой. После этого обычно достаточно писать `git push`.

`push` не отправляет просто «все файлы»: он публикует коммиты, которых ещё нет на удалённой стороне.

## 9. Получение изменений — fetch и pull

```bash
git fetch origin
```
Скачивает новые сведения и коммиты с удалённого репозитория, но не объединяет их с текущей локальной веткой. Это безопасный способ сначала узнать, что появилось на сервере.

```bash
git pull
```
Получает изменения с удалённого репозитория и интегрирует их в текущую ветку. Обычно это fetch + merge; поведение можно настроить.

```bash
git pull --ff-only
```
Обновляет текущую ветку только если возможно простое перемещение указателя вперёд (fast-forward). Если нужна сложная интеграция, команда остановится, не создавая merge автоматически.

**Важно:** перед `pull` я проверяю `git status`, чтобы не потерять или не перепутать локальные изменения.

## 10. Ветки — branch

Ветка позволяет вести отдельную линию разработки. Например, новая функция делается в `feature/search`, не затрагивая стабильную `main`.

```bash
git branch
```
Показывает локальные ветки. Звёздочка отмечает текущую.

```bash
git switch -c feature/search
```
Создаёт ветку `feature/search` и сразу переключается на неё.

```bash
git switch main
```
Переключается на существующую ветку `main`.

```bash
git branch -d feature/search
```
Удаляет локальную ветку, если Git считает её уже слитой.

Ветку обычно создают от актуальной `main`:
```bash
git switch main
git pull --ff-only
git switch -c feature/my-task
```

## 11. Объединение веток — merge

```bash
git switch main
git merge feature/search
```
Переключаемся на `main` и объединяем в неё изменения из `feature/search`.

Если истории можно просто соединить перемещением указателя, получится fast-forward. Если обе ветки развивались независимо, Git может создать merge commit.

После успешного слияния ветку можно удалить, если она больше не нужна.

## 12. Rebase — перенос коммитов

```bash
git switch feature/search
git rebase main
```
Переносит коммиты feature-ветки так, будто работа началась от актуальной `main`. История становится линейнее, но идентификаторы перенесённых коммитов меняются.

Не переписывай rebase общие ветки, которыми пользуются другие разработчики, без согласования.

## 13. Конфликты слияния

Конфликт возникает, когда Git не может автоматически решить, как объединить изменения. Например, две ветки я изменяюли одну и ту же строку.

В файле можно увидеть маркеры:
```text
<<<<<<< HEAD
текущий вариант
=======
вариант из другой ветки
>>>>>>> feature/search
```

Что делать:
1. Я открываю конфликтный файл.
2. Я выбираю правильный итоговый код или объедини оба изменения.
3. Удали маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
4. Запусти тесты.
5. Выполни `git add <файл>`.
6. Заверши merge коммитом или продолжи rebase через `git rebase --continue`.

Не выбирай вариант вслепую: можно случайно удалить нужную логику.

## 14. Отмена изменений

```bash
git restore Main.java
```
Отменяет незакоммиченные изменения файла в рабочей директории, возвращая содержимое из индекса. Изменения могут быть потеряны.

```bash
git restore --staged Main.java
```
Убирает изменения файла из staging, но оставляет их в рабочей директории.

```bash
git revert <commit-hash>
```
Создаёт новый коммит, который отменяет изменения указанного коммита. Подходит для уже опубликованной истории.

```bash
git reset --soft HEAD~1
```
Перемещает текущую ветку на предыдущий коммит, сохраняя изменения в staging.

```bash
git reset --mixed HEAD~1
```
Перемещает ветку назад, оставляя изменения в рабочей директории, но убирая их из staging. Это поведение по умолчанию у reset.

```bash
git reset --hard HEAD~1
```
Перемещает ветку назад и удаляет изменения из индекса и рабочей директории. Опасная команда: незакоммиченная работа может быть потеряна.

Если коммит уже отправлен на GitHub и им могут пользоваться другие, обычно безопаснее `git revert`, а не переписывание истории через reset + force push.

## 15. .gitignore

`.gitignore` сообщает Git, какие **неотслеживаемые** файлы не нужно предлагать к добавлению.

Типичные записи:
```gitignore
.idea/
*.iml
target/
out/
*.log
.env
```

Важно: если файл уже отслеживается Git, добавление его в `.gitignore` само по себе не прекратит отслеживание.

```bash
git rm --cached file.txt
```
Убирает файл из Git-индекса, но оставляет его на компьютере.

```bash
git rm -r --cached .idea
```
Убирает папку из индекса рекурсивно, не удаляя локальные файлы.

Я не добавляю в репозиторий пароли, токены, приватные ключи и реальные `.env`.

## 16. Типичный рабочий сценарий через Pull Request

```bash
git switch main
git pull --ff-only
git switch -c feature/add-search

# изменяешь код
git status
git diff
git add src/
git diff --staged
git commit -m "Add task search"
git push -u origin feature/add-search
```

Затем на GitHub:
1. Я создаю Pull Request из `feature/add-search` в `main`.
2. Опиши, что сделано и как проверить.
3. Дождись проверок CI и review.
4. Исправь замечания, если они есть.
5. После одобрения выполни merge.
6. Обнови локальную `main`: `git switch main` и `git pull --ff-only`.

## 17. Частые ошибки

- **Закоммитил не всё:** перед commit проверяй `git status` и `git diff --staged`.
- **Пушишь не ту ветку:** я проверяю `git branch --show-current`.
- **Pull не проходит из-за локальных изменений:** сначала соя храню их коммитом или аккуратно я использую stash.
- **Файл игнорируется, но всё ещё на GitHub:** он уже отслеживается; нужен `git rm --cached`.
- **Конфликт:** не удаляй маркеры механически, сначала собери правильный итоговый код.
- **`push` отклонён:** удалённая ветка содержит новые коммиты. Сделай fetch, изучаю изменения и интегрируй их; я не использую force push наугад.

## 18. Полезные команды

```bash
git branch --show-current   # текущая ветка
git show <commit>           # подробности коммита
git diff main..feature      # разница между ветками
git stash                   # временно убрать незакоммиченные изменения
git stash pop               # вернуть сохранённые изменения
git remote -v               # адреса remote
git clean -n                # показать неотслеживаемые файлы, которые будут удалены
```

`git clean -n` только показывает, что будет удалено. `git clean -fd` реально удаляет неотслеживаемые файлы и папки — я использую осторожно.

## Практика

1. Я создаю тестовый репозиторий.
2. Я добавляю README и сделай первый коммит.
3. Я создаю ветку `feature/about`.
4. Я изменяю README, сделай коммит и отправь ветку на GitHub.
5. Я создаю Pull Request и слей его.
6. Я изменяю файл в двух ветках по-разному и специально вызови конфликт.
7. Разреши конфликт и я проверяю итог.
8. Я создаю коммит с ошибкой и отмени его через `git revert`.

## 19. HEAD, origin и origin/main — что означают

- `HEAD` — указатель на то, где ты сейчас работаешь. Обычно он указывает на текущую локальную ветку.
- `main` — локальная ветка на твоём компьютере.
- `origin` — короткое имя удалённого репозитория. Это не специальное слово Git, а обычное соглашение.
- `origin/main` — remote-tracking branch: локальная запись о состоянии ветки `main` на сервере после последнего `fetch`.

Посмотреть ветки:
```bash
git branch       # локальные ветки
git branch -r    # удалённые ветки, известные локальному Git
git branch -a    # локальные и remote-tracking ветки
git branch -vv   # связь локальных веток с upstream и статус относительно них
```

Важно: `origin/main` не обновляется сам по себе. Сначала выполни `git fetch origin`.

## 20. Upstream и отслеживаемая ветка

Upstream — удалённая ветка, с которой связана локальная. Она позволяет Git понимать, откуда получать изменения и куда отправлять их по умолчанию.

```bash
git push -u origin feature/search
```
Флаг `-u` (`--set-upstream`) задаёт upstream. После этого для этой ветки обычно работают короткие `git push` и `git pull`.

## 21. Временное сохранение — stash

`stash` временно убирает незакоммиченные изменения, чтобы можно было переключить ветку или обновить проект.

```bash
git stash push -m "work in progress"  # сохранить изменения с подписью
git stash list                         # список сохранений
git stash show -p stash@{0}            # посмотреть содержимое
git stash apply stash@{0}              # применить, но оставить в списке
git stash pop                          # применить последнее и убрать его из списка
git stash drop stash@{0}               # удалить запись
```

`stash` не заменяет коммит и не является надёжным архивом работы. Новые неотслеживаемые файлы по умолчанию могут не попасть в stash; для них есть `-u`.

## 22. Поиск потерянного коммита — reflog

```bash
git reflog
```
Показывает недавние перемещения `HEAD` и указателей веток в локальном репозитории. Полезно, если после `reset` или неудачного rebase кажется, что коммит пропал. Пока объект не удалён сборкой мусора, его часто можно восстановить по hash из reflog.

## 23. Cherry-pick и теги

```bash
git cherry-pick <commit-hash>
```
Применяет изменения одного существующего коммита к текущей ветке и создаёт новый коммит. Не копирует ветку целиком.

```bash
git tag v1.0.0
git tag -a v1.0.0 -m "First release"
git push origin v1.0.0
```
Тег помечает конкретный коммит, например релиз. Обычный `git push` не всегда отправляет теги автоматически; их можно отправить отдельно.

## 24. Force push — почему опасен

```bash
git push --force-with-lease
```
Используется после намеренного переписывания истории своей ветки. Он может заменить историю удалённой ветки. `--force-with-lease` безопаснее простого `--force`: Git проверяет, что удалённая ветка не я изменяюлась неожиданно с момента последнего получения данных. Но это всё равно не команда на каждый день. Я не делаю force push в общую ветку и я не использую его, не понимая последствий.

## 25. Detached HEAD

Detached HEAD — состояние, когда `HEAD` указывает прямо на коммит, а не на имя ветки. Можно изучать старую версию, но новые коммиты не будут автоматически принадлежать обычной ветке. Если хочешь сохранит работу, я создаю ветку: `git switch -c save-my-work`.

## 26. Разбор типичных сообщений Git

- `nothing to commit, working tree clean` — нет изменений для коммита.
- `Changes not staged for commit` — файлы изменены, но ещё не добавлены через `git add`.
- `Untracked files` — новые файлы, Git пока не отслеживает.
- `rejected (non-fast-forward)` — на сервере есть коммиты, которых нет локально; сначала получи и изучаю их.
- `CONFLICT` — Git не смог автоматически объединить изменения; разреши конфликт вручную.

Перед любой рискованной командой: `git status`, `git diff`, при необходимости я создаю резервную ветку или коммит.


## 27. Ещё несколько повседневных команд

```bash
git mv old-name.java new-name.java
git rm file.txt
git commit --amend
```
- `git mv` переименовывает/перемещает файл и обновляет индекс Git. Git обычно и сам распознаёт переименование по сравнению содержимого, поэтому команда не обязательна.
- `git rm` удаляет файл из рабочей папки и из индекса. `git rm --cached` убирает только из индекса, оставляя локальный файл.
- `git commit --amend` заменяет последний коммит новым (например, меняет сообщение или добавляет забытые staged-изменения). Если старый коммит уже опубликован, amend переписывает историю и требует особой осторожности.

## 28. Как безопасно понять, что произойдёт

```bash
git status
git diff
git diff --staged
git log --oneline --decorate -5
git clean -n
```
Эти команды помогают осмотреть состояние до изменений. `git clean -n` — предварительный просмотр неотслеживаемых файлов, которые удалил бы `git clean`; сам по себе ничего не удаляет.

Я не запускаю `reset --hard`, `clean -fd` и `push --force` по инструкции, не понимая, какие именно данные они затронут.
